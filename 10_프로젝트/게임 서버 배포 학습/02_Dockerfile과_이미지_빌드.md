# 2단계 — Dockerfile과 이미지 빌드

상위 문서: [[00_프로젝트_홈|게임 서버 배포 학습]]  
이전 단계: [[01_이미지와_컨테이너]]

## 이번 단계의 목표

이 문서를 읽은 뒤에는 다음 흐름을 자신의 말로 설명할 수 있어야 한다.

```text
소스·에셋·기본 설정·빌드 버전
  → 빌드 컨텍스트 준비
  → 의존성 복원
  → 세 서버 게시
  → 실행에 필요한 파일만 최종 이미지에 복사
  → 런타임 이미지 완성
```

이번 단계의 핵심 질문은 두 가지다.

1. Dockerfile은 어떤 입력을 받아 어떻게 이미지로 바꾸는가?
2. 하나의 이미지 안에 세 서버가 들어가면서도 컨테이너마다 다른 서버를 실행할 수 있는 이유는 무엇인가?

아직 Harbor에 저장하거나 Kubernetes에서 실행하지 않는다. 이번 장의 끝은 **로컬 빌드 결과로 런타임 이미지가 완성되는 지점**이다.

## 1. 이것이 무엇인가

### Dockerfile

Dockerfile은 Docker 이미지를 만드는 절차를 선언한 텍스트 파일이다. 다음과 같은 작업을 순서대로 적는다.

- 어떤 기반 이미지에서 시작할지 정한다.
- 빌드에 필요한 파일을 복사한다.
- 의존성을 내려받고 서버를 컴파일한다.
- 최종 이미지에 필요한 파일만 골라 넣는다.
- 컨테이너 시작 시 사용할 기본 명령을 정한다.

Dockerfile을 요리법에 비유하면, 이미지는 그 요리법과 준비된 재료로 만든 완성품이다. 요리법만 있어서는 완성품이 나오지 않으며, 소스 코드와 에셋 같은 재료도 필요하다.

### Docker build

Docker build는 Dockerfile과 필요한 파일을 읽어 이미지 레이어를 차례로 만드는 작업이다.

```text
Dockerfile + 빌드 컨텍스트 + 빌드 인자
  → Docker build
  → 로컬 이미지
```

여기서 만들어진 이미지는 아직 Harbor에 올라간 것이 아니다. 빌드와 레지스트리 업로드는 서로 다른 작업이다.

### 빌드 컨텍스트

빌드 컨텍스트(Build Context)는 Docker build가 읽을 수 있도록 넘겨주는 파일 묶음과 그 기준 디렉터리다.

Dockerfile의 `COPY`는 컴퓨터 전체에서 마음대로 파일을 가져올 수 없다. 원칙적으로 빌드 컨텍스트 안에 준비된 파일만 이미지에 복사할 수 있다. 따라서 실제 빌드 스크립트는 Docker build를 시작하기 전에 필요한 내용을 한곳에 모은다.

게임 서버 프로젝트의 공개용 구조로 표현하면 다음과 같다.

```text
임시 빌드 컨텍스트
  ├─ Dockerfile
  ├─ 서버 소스
  ├─ 서버가 참조하는 공유 소스
  ├─ 빌드 도구 소스
  ├─ 이미지에 포함할 서버 에셋
  └─ 컨테이너용 기본 설정
```

빌드 컨텍스트에 파일이 빠지면 Dockerfile이 그 파일을 복사하거나 빌드할 수 없다. 반대로 불필요하거나 민감한 파일을 넣으면 이미지에 들어가거나 빌드 시스템으로 전달될 위험이 있다.

### 멀티 스테이지 빌드

멀티 스테이지 빌드는 하나의 Dockerfile을 여러 작업 단계로 나누는 방법이다.

서버를 빌드할 때는 컴파일러와 SDK가 필요하지만 실행할 때는 더 작은 Runtime만 있으면 된다. 그래서 무거운 빌드 환경에서 결과물을 만든 뒤, 최종 이미지에는 그 결과물만 옮긴다.

```text
빌드용 환경: SDK + 소스 + 빌드 도구
              ↓ 게시 결과만 전달
실행용 환경: Runtime + 게시 결과 + 실행에 필요한 파일
```

중간 단계는 최종 이미지에 통째로 들어가지 않는다. 최종 이미지가 어떤 단계에서 무엇을 복사했는지가 중요하다.

## 2. 왜 필요한가

서버 소스만 다른 장비에 복사하면 그 장비에도 올바른 SDK, 라이브러리, 빌드 도구와 설정이 있어야 한다. 장비마다 환경이 다르면 빌드와 실행 결과도 달라질 수 있다.

Dockerfile로 제작 과정을 고정하면 다음 효과를 얻는다.

- TeamCity와 개발 환경이 같은 이미지 제작 절차를 사용할 수 있다.
- 빌드에 사용한 SDK 환경을 명확히 정할 수 있다.
- 세 서버를 동일한 소스 리비전과 빌드 버전으로 게시할 수 있다.
- 실행에 필요하지 않은 소스와 SDK를 최종 이미지에서 제외할 수 있다.
- 완성된 이미지를 Harbor에 보관하고 여러 노드에서 반복 실행할 수 있다.

게임 서버 프로젝트에서는 세 서버가 공유하는 코드와 라이브러리가 많다. 세 서버를 하나의 런타임 이미지에 넣으면 같은 리비전의 공통 파일을 함께 전달할 수 있다.

다만 이 선택에는 대가도 있다.

- 서버 하나만 수정해도 공용 이미지 전체를 다시 만들 수 있다.
- 이미지 안에 세 서버의 결과물이 모두 들어가므로 단일 서버 전용 이미지보다 클 수 있다.
- 어떤 서버를 실행할지는 이미지가 아니라 컨테이너 실행 명령에서 정확히 선택해야 한다.

## 3. 주요 구성 요소

현재 확인한 서버용 Dockerfile은 논리적으로 네 단계로 나뉜다. 실제 내부 이름과 경로는 공개용 역할명으로 바꿔 설명한다.

### 1단계: build — 빌드 환경 준비

빌드 단계는 .NET SDK가 설치된 가벼운 Linux 기반 이미지에서 시작한다.

주요 작업은 다음과 같다.

1. 빌드에 필요한 기본 환경을 준비한다.
2. 서버 소스, 공유 소스, 빌드 도구 소스를 빌드 컨텍스트에서 복사한다.
3. ControlServer, GameWorker, GatewayServer의 외부 패키지를 복원한다.

여기서 `restore`는 서버를 실행하는 작업이 아니다. 각 프로젝트가 참조하는 외부 패키지를 내려받아 다음 컴파일 단계가 가능하게 만드는 작업이다.

### 2단계: publish — 세 서버를 실행 가능한 결과로 게시

publish 단계는 build 단계를 이어받는다. 이미 복사한 소스와 복원한 패키지를 그대로 사용해 서버 세 종류를 게시한다.

```text
ControlServer 프로젝트  ─┐
GameWorker 프로젝트     ─┼→ 공통 게시 디렉터리
GatewayServer 프로젝트  ─┘
```

`.NET publish`는 단순히 소스 파일을 복사하는 것이 아니다. 소스를 컴파일하고 실행에 필요한 어셈블리와 의존 파일을 게시 디렉터리에 모은다.

세 서버가 공유하는 어셈블리가 많기 때문에 현재 구조는 세 게시 결과를 같은 디렉터리에 모은다. 또한 빌드 스크립트가 계산한 빌드 버전을 각 서버의 버전 정보에 전달한다.

중요한 점은 **이 단계에서 세 서버가 동시에 실행되는 것이 아니라 세 서버의 실행 파일이 함께 준비되는 것**이다.

### 3단계: base — 실행 환경 준비

base 단계는 SDK가 아니라 더 작은 .NET Runtime 기반 이미지에서 시작한다.

주요 작업은 다음과 같다.

- 서버 실행에 필요한 운영체제 라이브러리를 설치한다.
- 문자 처리와 시간대 같은 실행 환경을 준비한다.
- 애플리케이션 작업 디렉터리와 로그용 기본 경로를 준비한다.

컴파일러나 전체 소스는 필요하지 않으므로 넣지 않는다. 이 단계는 “서버 프로그램은 아직 없지만 실행할 바닥은 준비된 상태”다.

### 4단계: final — 최종 런타임 이미지 조립

final 단계는 base 실행 환경 위에서 완성된다.

```text
base 실행 환경
  + publish 단계의 세 서버 결과물
  + 실행에 필요한 서버 에셋
  + 컨테이너용 기본 설정
  + 기본 실행 명령
  = 최종 런타임 이미지
```

최종 단계에서는 보안을 위해 일반 사용자 권한으로 실행하도록 전환한다. 컨테이너가 항상 관리자 권한으로 실행될 필요는 없기 때문이다.

기본 실행 명령은 ControlServer 역할의 실행 파일을 시작하도록 되어 있다. GameWorker나 GatewayServer 컨테이너를 만들 때는 외부 배포 설정이 이 기본 명령을 다른 서버 실행 파일로 바꾼다.

```text
같은 최종 이미지
  ├─ 기본 명령                  → ControlServer 실행
  ├─ GameWorker 명령으로 교체   → GameWorker 실행
  └─ GatewayServer 명령으로 교체 → GatewayServer 실행
```

서버 ID나 환경 설정이 서버 종류를 선택하는 것이 아니다. **어떤 실행 파일을 시작하라는 명령이 서버 종류를 결정한다.** ID와 환경 설정은 같은 종류로 실행된 서버 인스턴스들을 구분하거나 동작을 조정할 때 사용한다.

### build argument — 빌드 시점에 전달하는 값

빌드 스크립트는 소스 리비전과 프로토콜 정보를 이용해 빌드 버전을 계산하고 Docker build에 전달한다. Dockerfile은 이 값을 세 서버의 버전 메타데이터에 넣는다.

이 값은 빌드할 때 사용하는 `ARG`에 해당한다. 컨테이너가 실행된 뒤 바꾸는 환경 변수와는 역할이 다르다.

| 구분 | 빌드 인자 | 실행 환경 변수 |
| --- | --- | --- |
| 적용 시점 | 이미지 빌드 중 | 컨테이너 실행 시 |
| 대표 용도 | 빌드 버전, 빌드 옵션 | 환경별 서버 설정 |
| 이미지를 다시 만들어야 하는가? | 값을 바꾸려면 보통 다시 빌드 | 같은 이미지에 다른 값을 줄 수 있음 |

## 4. 다른 기술과 어떤 관계인가

이미지 빌드는 전체 배포 흐름의 중간 단계다.

```text
소스 저장소
  → TeamCity가 빌드 스크립트 실행
  → 빌드 컨텍스트 준비
  → Dockerfile로 이미지 빌드
  → 이미지 산출물 생성
  → Harbor push                  ← 3단계에서 학습
  → Kubernetes에서 컨테이너 실행 ← 4단계 이후 학습
```

| 기술 | 이번 단계에서의 역할 |
| --- | --- |
| 소스 버전 관리 | 빌드할 소스 리비전을 제공 |
| TeamCity | 빌드 환경 변수와 리비전을 전달하고 빌드 스크립트를 실행 |
| 빌드 스크립트 | 필요한 파일을 빌드 컨텍스트로 모으고 빌드 버전을 계산 |
| Dockerfile | 컨텍스트를 이미지로 바꾸는 단계별 절차를 정의 |
| Docker 엔진 | Dockerfile의 절차를 실제로 실행하고 로컬 이미지를 생성 |
| Harbor | 다음 단계에서 완성된 이미지를 저장하고 배포 대상에 제공 |

확인된 빌드 흐름에서는 이미지 빌드와 Harbor push가 분리되어 있다. 빌드된 이미지를 파일 형태의 산출물로 넘겼다가 다음 작업에서 불러와 태그를 붙이고 push할 수 있다. 따라서 **Docker build 성공과 Harbor 저장 성공은 서로 다른 상태**다.

## 5. 실제 프로젝트에서는 어디에 사용되는가

2026-08-20 로컬 소스의 빌드 스크립트와 서버용 Dockerfile을 기준으로 다음 흐름을 확인했다.

1. 빌드 스크립트가 소스 리비전과 프로토콜 정보를 조합해 빌드 버전을 만든다.
2. 임시 빌드 컨텍스트를 초기화한다.
3. 서버 소스, 필요한 공유 소스, 빌드 도구, 서버 에셋을 컨텍스트에 복사한다.
4. 컨테이너용 기본 설정과 대상 아키텍처의 Dockerfile을 컨텍스트에 둔다.
5. Docker build에 빌드 버전을 전달한다.
6. Dockerfile이 세 서버의 패키지를 복원하고 같은 버전으로 게시한다.
7. 실행 Runtime, 세 서버 결과물, 필요한 에셋과 기본 설정을 최종 이미지에 조립한다.
8. 기본 실행 명령을 ControlServer로 지정한다.
9. 빌드가 성공하면 다음 저장 단계에서 사용할 이미지 산출물을 만든다.

현재 Dockerfile은 소스의 넓은 범위를 복사한 뒤 패키지를 복원한다. 구조가 단순하고 필요한 파일이 빠질 가능성은 줄지만, 소스 파일 하나가 바뀌어도 패키지 복원 단계의 캐시가 무효화될 수 있다. 현재 스냅샷은 세밀한 캐시 최적화보다 첫 빌드의 안정성을 우선한 구조로 확인된다.

설정과 에셋에 대해서는 다음 경계를 기억한다.

- 이미지에는 실행에 필요한 기본 설정과 서버 에셋 일부가 들어간다.
- 환경별 설정과 민감 정보는 이미지에 고정하면 안 되며 실행 시 외부에서 주입해야 한다.
- 하나의 전체 릴리스에는 이미지와 별도 경로로 전달되는 에셋·DB 산출물도 있을 수 있다.
- 실제 설정값이나 인증 정보는 공개 학습 문서에 기록하지 않는다.

## 6. 반드시 이해해야 할 핵심

1. **Dockerfile만으로 이미지를 만들 수는 없다.** Dockerfile과 빌드 컨텍스트, 필요하면 빌드 인자가 함께 입력된다.
2. **빌드 컨텍스트는 Dockerfile이 접근할 수 있는 파일 범위다.** 빌드 스크립트가 필요한 소스와 에셋을 먼저 모은다.
3. **멀티 스테이지 빌드는 빌드 환경과 실행 환경을 분리한다.** SDK와 소스는 빌드에 사용하고 최종 이미지에는 Runtime과 게시 결과 중심으로 넣는다.
4. **restore와 publish는 다르다.** restore는 외부 패키지를 준비하고 publish는 소스를 컴파일해 실행 결과를 모은다.
5. **세 서버의 실행 결과가 하나의 이미지에 함께 들어간다.** 이미지 하나가 세 서버를 동시에 실행하는 것은 아니다.
6. **서버 종류는 실행 명령으로 선택한다.** 설정 ID가 ControlServer를 GameWorker로 바꾸는 것은 아니다.
7. **빌드 버전은 이미지 제작 시 세 서버 결과에 함께 반영된다.** 동일 리비전으로 만들어졌는지 추적하는 근거가 된다.
8. **이미지 빌드와 Harbor push는 별도 단계다.** 로컬 이미지가 만들어졌다고 배포 가능한 레지스트리에 저장된 것은 아니다.

한 문장으로 압축하면 다음과 같다.

> 빌드 스크립트가 준비한 소스·에셋·설정·버전을 Dockerfile의 멀티 스테이지 절차로 처리해, 세 서버의 실행 결과와 작은 Runtime을 담은 하나의 재사용 가능한 이미지를 만든다.

## 7. 지금 단계에서 몰라도 되는 내용

다음 내용은 뒤에서 다루므로 지금 외울 필요가 없다.

- Harbor의 repository, tag, push, pull — 3단계
- Kubernetes가 이미지를 받아 실행하는 과정 — 4단계 이후
- Pod, Deployment, Rollout — 5단계와 11단계
- ConfigMap과 Secret을 이용한 환경별 설정 주입 — 7단계
- 이미지 레이어의 실제 저장 드라이버 구현
- 고급 BuildKit 캐시 마운트와 원격 캐시
- 멀티 아키텍처 이미지와 cross-build
- 세부 .NET publish 옵션과 어셈블리 버전 형식

이번에는 `입력 묶음 → 네 단계의 Dockerfile → 최종 이미지`만 이해하면 된다.

## 8. 스스로 확인할 질문

1. Dockerfile과 Docker 이미지의 관계는 무엇인가?
2. 빌드 컨텍스트란 무엇이며, 왜 필요한가?
3. 빌드용 SDK 이미지를 그대로 최종 이미지로 사용하지 않는 이유는 무엇인가?
4. `restore`와 `publish`는 각각 무엇을 하는가?
5. 세 서버를 같은 게시 디렉터리에 모았다는 것은 세 서버가 동시에 실행된다는 뜻인가?
6. 같은 최종 이미지에서 ControlServer, GameWorker, GatewayServer 중 하나를 선택해 실행하는 방법은 무엇인가?
7. 빌드 인자와 컨테이너 실행 환경 변수는 적용 시점이 어떻게 다른가?
8. Docker build가 성공해도 Harbor에 이미지가 없을 수 있는 이유는 무엇인가?
9. 현재 구조에서 소스 파일 변경이 패키지 복원 캐시에 영향을 줄 수 있는 이유는 무엇인가?

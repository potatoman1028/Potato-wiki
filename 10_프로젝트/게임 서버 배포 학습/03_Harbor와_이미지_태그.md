# 3단계 — Harbor와 이미지 태그

상위 문서: [[00_프로젝트_홈|게임 서버 배포 학습]]  
이전 단계: [[02_Dockerfile과_이미지_빌드]]

## 이번 단계의 목표

이 문서를 읽은 뒤에는 다음 흐름을 자신의 말로 설명할 수 있어야 한다.

```text
TeamCity가 만든 로컬 이미지
  → 이미지 산출물 전달
  → 업로드 작업에서 이미지 불러오기
  → Harbor 주소와 리비전 태그 지정
  → Harbor에 push
  → 배포 시스템이 같은 이름과 태그로 이미지 식별
```

이번 단계의 핵심 질문은 세 가지다.

1. Harbor에는 컨테이너가 아니라 무엇이 저장되는가?
2. 이미지 이름과 태그는 어떤 이미지를 실행할지 어떻게 가리키는가?
3. 리비전 기반 태그를 사용해야 빌드 결과와 소스 변경을 추적하기 쉬운 이유는 무엇인가?

## 1. 이것이 무엇인가

### 컨테이너 레지스트리

컨테이너 레지스트리(Container Registry)는 Docker 이미지를 저장하고 배포하는 서버다.

2단계에서 Docker build가 만든 이미지는 빌드 장비의 로컬 Docker 저장소에만 존재한다. 다른 빌드 장비나 Kubernetes 노드는 그 로컬 이미지에 직접 접근할 수 없다. 이미지를 공용으로 가져갈 수 있는 레지스트리에 올려야 한다.

```text
빌드 장비의 로컬 이미지
  ── push ──▶ 컨테이너 레지스트리
                 │
                 ├── pull ──▶ 개발자 장비
                 ├── pull ──▶ 테스트 장비
                 └── pull ──▶ Kubernetes 노드
```

레지스트리에는 실행 중인 컨테이너가 저장되는 것이 아니다. 컨테이너를 만들 수 있는 **이미지와 그 메타데이터**가 저장된다.

### Harbor

Harbor는 조직이 직접 운영할 수 있는 컨테이너 레지스트리 제품이다. 표준 컨테이너 이미지를 저장하는 기능에 조직용 관리 기능을 더한다.

- 사용자와 로봇 계정의 접근 권한 관리
- 프로젝트와 repository 단위의 이미지 분류
- 이미지 취약점 검사
- 이미지 복제와 보존 정책
- 태그 불변성 정책
- 이미지 push와 pull 기록 확인

모든 기능을 현재 게임 서버 프로젝트가 사용한다고 단정할 수는 없다. 이번 단계에서는 **사설 이미지 저장소와 배포 이미지의 기준점**이라는 역할에 집중한다.

### Docker Hub와 Harbor의 차이

둘 다 컨테이너 레지스트리 역할을 할 수 있지만 운영 주체와 사용 목적이 다르다.

| 구분 | Docker Hub | Harbor |
| --- | --- | --- |
| 운영 주체 | 외부 공개 서비스 | 조직이 직접 설치·운영 가능 |
| 대표 용도 | 공개 기반 이미지와 범용 이미지 배포 | 사내 애플리케이션 이미지 관리 |
| 접근 주소 | Docker Hub가 제공 | 조직이 정한 사설 주소 |
| 권한·정책 | 서비스가 제공하는 범위 사용 | 조직 정책에 맞춰 세부 설정 가능 |

게임 서버 이미지처럼 공개하면 안 되는 내부 빌드 결과는 사설 Harbor에 보관하는 것이 자연스럽다.

### Harbor에 실제로 저장되는 것

이미지는 단일 실행 파일 하나가 아니라 여러 레이어와 설명 정보로 구성된다.

Harbor에는 논리적으로 다음 내용이 저장된다.

- 이미지 레이어: Runtime, 라이브러리, 게시된 서버 파일 등
- 이미지 설정: 기본 실행 명령과 이미지 환경 정보
- manifest: 어떤 레이어와 설정이 하나의 이미지를 구성하는지 나타내는 목록
- tag: 사람이 이해하기 쉬운 이미지 버전 이름
- digest: 이미지 내용을 기준으로 계산한 변경 불가능한 식별값
- 생성 시각, 크기, 검사 결과 같은 부가 메타데이터

소스 저장소의 commit이나 실행 중인 컨테이너 자체를 저장하는 곳은 아니다. 이미지 안에 최종 서버 파일이 들어 있고, 그 이미지를 다시 내려받을 수 있게 보관하는 곳이다.

## 2. 왜 필요한가

빌드 장비의 로컬 저장소만 사용하면 다음 문제가 생긴다.

- 빌드 장비가 바뀌면 이미지를 찾을 수 없다.
- 여러 Kubernetes 노드가 같은 이미지를 받을 공통 위치가 없다.
- 어떤 이미지가 어떤 서버 버전인지 추적하기 어렵다.
- 이전 이미지로 돌아가야 할 때 빌드 장비의 로컬 상태에 의존하게 된다.
- 개발, 테스트, 운영 주체마다 이미지를 임의로 복사해야 한다.

Harbor를 사용하면 이미지의 저장과 실행을 분리할 수 있다.

```text
TeamCity의 책임: 이미지를 만들어 Harbor에 올린다.
Harbor의 책임: 올린 이미지를 이름과 버전별로 보관하고 제공한다.
배포 시스템의 책임: 실행할 이미지 이름과 버전을 지정한다.
```

이 역할 분리 덕분에 Kubernetes는 TeamCity가 어디에서 어떻게 이미지를 만들었는지 몰라도 된다. Harbor의 이미지 주소만 알면 된다.

## 3. 주요 구성 요소

### 이미지 주소의 구조

공개용 예시 이미지 주소를 살펴보자.

```text
registry.example.com/game/runtime-<environment>-<architecture>:rev-12345
└──── registry ────┘ └──────── repository ─────────┘ └── tag ──┘
```

| 구성 | 예시 | 의미 |
| --- | --- | --- |
| Registry | `registry.example.com` | 이미지를 보관하는 Harbor 서버 주소 |
| Harbor Project 또는 Namespace | `game` | repository를 묶고 권한을 나누는 논리 영역 |
| Repository | `runtime-<environment>-<architecture>` | 같은 종류의 이미지 버전들이 모이는 이름 |
| Tag | `rev-12345` | repository 안에서 특정 빌드를 가리키는 사람이 읽기 쉬운 이름 |

여기서 Harbor의 `Project`는 우리가 학습하는 게임 프로젝트와 다른 용어다. Harbor 안에서 repository와 권한을 묶는 공간을 뜻한다.

### Repository와 Tag

Repository는 같은 목적을 가진 이미지들의 계보이고, tag는 그중 특정 버전에 붙인 이름이다.

```text
runtime-dev-x64 repository
  ├─ rev-12343
  ├─ rev-12344
  └─ rev-12345
```

`runtime-dev-x64`은 “무슨 이미지인가”를 나타내고, `rev-12345`는 “어느 빌드인가”를 나타낸다.

### Tag와 Digest

tag와 digest는 모두 이미지를 식별하지만 성격이 다르다.

| 구분 | Tag | Digest |
| --- | --- | --- |
| 형태 | 사람이 정한 이름 | 이미지 내용으로 계산한 해시 |
| 읽기 쉬움 | 쉬움 | 어려움 |
| 변경 가능성 | 같은 tag를 다른 이미지에 다시 붙일 수 있음 | 내용이 달라지면 digest도 반드시 달라짐 |
| 대표 용도 | 릴리스 버전과 리비전 표현 | 정확히 동일한 이미지 검증 |

예를 들어 `rev-12345`라는 tag는 빌드 리비전을 이해하기 쉽다. 그러나 레지스트리 정책이 허용하면 같은 tag를 새 이미지에 다시 붙여 덮어쓸 수 있다.

digest는 다음과 같은 형태다.

```text
sha256:<이미지 내용으로 계산된 해시>
```

동일한 내용이면 동일한 digest를 가리키고, 내용이 달라지면 digest도 달라진다. 따라서 정확한 이미지 내용 확인에는 digest가 가장 강한 식별자다.

### Push와 Pull

두 동작의 방향을 구분한다.

- push: 로컬 이미지를 Harbor로 올린다.
- pull: Harbor의 이미지를 실행할 장비로 내려받는다.

```text
TeamCity ── push ──▶ Harbor ── pull ──▶ Kubernetes 노드
```

push하려면 보통 다음 조건이 필요하다.

- 올바른 Harbor 주소
- push 권한이 있는 인증 정보
- Harbor 주소를 포함한 이미지 이름
- 올바른 repository와 tag
- Harbor까지의 네트워크 연결

인증 정보는 소스, Dockerfile, 이미지, 로그에 기록하지 않고 CI의 안전한 비밀 변수로 전달해야 한다.

### 리비전 기반 태그

`latest`처럼 의미가 변하는 이름만 사용하면 현재 실행 중인 이미지가 어느 소스에서 만들어졌는지 찾기 어렵다.

리비전 기반 tag는 소스 변경 번호와 이미지 사이에 추적 가능한 연결을 만든다.

```text
소스 리비전 12345
  → 이미지 빌드
  → tag: rev-12345
  → 배포 설정도 rev-12345 지정
```

이렇게 하면 다음 질문에 답하기 쉬워진다.

- 이 Pod가 어떤 소스 변경으로 만들어졌는가?
- 이전 릴리스의 이미지는 무엇인가?
- 빌드 로그와 이미지가 같은 리비전을 가리키는가?
- 롤백할 때 어느 tag로 돌아가야 하는가?

### 동일 태그 덮어쓰기의 위험

리비전 tag를 사용하더라도 같은 tag로 다시 push할 수 있다면 완전한 불변성은 보장되지 않는다.

```text
오전의 rev-12345 → digest A
오후에 같은 tag로 재빌드·덮어쓰기 → digest B
```

이 경우 같은 `rev-12345`라는 이름이 시간에 따라 다른 내용을 뜻하게 된다.

- 서버마다 캐시된 이미지가 달라질 수 있다.
- 장애 시 실제로 어떤 내용을 실행했는지 판단하기 어려워진다.
- tag만 기록한 배포 이력으로 정확한 롤백을 보장하기 어렵다.

따라서 일반적으로 다음 원칙을 함께 사용한다.

- 빌드마다 고유한 tag를 발급한다.
- 리비전 tag를 재사용하지 않는다.
- Harbor의 불변 tag 정책을 검토한다.
- 중요한 검증에는 digest도 기록한다.

현재 Harbor의 불변 tag 정책 적용 여부는 로컬 소스만으로 확인할 수 없으므로 `외부 확인 필요`다.

## 4. 다른 기술과 어떤 관계인가

Harbor는 CI와 배포 시스템 사이의 이미지 전달 경계다.

```text
소스 리비전
  → TeamCity
  → Docker build
  → runtime 이미지
  → Harbor repository:tag
  → 배포 설정에서 repository와 tag 지정
  → ArgoCD가 설정 변경 감지
  → Kubernetes 노드가 Harbor에서 pull
```

| 기술 | Harbor 이미지와의 관계 |
| --- | --- |
| TeamCity | 이미지를 빌드하고 Harbor에 push하는 작업을 자동화 |
| Docker | 이미지를 만들고 tag를 붙이며 push·pull하는 표준 동작 제공 |
| Harbor | 이미지 레이어와 manifest를 repository·tag별로 보관 |
| Helm values | 나중에 실행할 image repository와 tag를 선언 |
| ArgoCD | Git에 기록된 이미지 tag 변경을 배포 변경으로 감지 |
| Kubernetes | 지정된 repository와 tag의 이미지를 Harbor에서 pull해 컨테이너 실행 |

Harbor에 이미지가 존재하는 것은 **배포 준비가 된 것**이지 **이미 배포됐다는 뜻**은 아니다. 배포 설정이 새 tag를 가리키고 ArgoCD와 Kubernetes가 그 변경을 적용해야 실제 서버가 바뀐다.

## 5. 실제 프로젝트에서는 어디에 사용되는가

2026-08-20 로컬 빌드·업로드 스크립트를 공개용으로 치환해 확인한 흐름은 다음과 같다.

### 이미지 빌드 작업

1. 소스 변경 번호를 사용해 `rev-<revision>` 형식의 tag를 만든다.
2. 논리 환경과 CPU 아키텍처가 구분되는 repository 이름을 만든다.
3. Docker build로 로컬 이미지를 생성한다.
4. 로컬 이미지를 파일 형태의 이미지 산출물로 저장하고 압축한다.
5. TeamCity가 이 산출물을 다음 업로드 작업에 전달한다.

### Harbor 업로드 작업

1. 전달받은 이미지 산출물이 정확히 하나인지 확인한다.
2. 압축을 풀고 이미지 파일을 로컬 Docker 저장소로 불러온다.
3. 이미지 이름 앞에 Harbor registry 주소를 붙인다.
4. 빌드에서 만들어진 리비전 tag가 유지되는지 확인한다.
5. CI의 보안 변수를 이용해 Harbor에 인증한다.
6. 최종 이미지 주소로 push한다.
7. push 성공 여부와 이미지 이름·tag를 빌드 기록에 남긴다.

공개용 형태로 압축하면 다음과 같다.

```text
runtime-<environment>-<architecture>:rev-<revision>
  → 이미지 파일 산출물
  → 업로드 작업에서 load
  → registry.example.com/game/runtime-<environment>-<architecture>:rev-<revision>
  → Harbor push
```

이 구조에서는 다음 실패가 서로 구분된다.

| 실패 지점 | 의미 |
| --- | --- |
| Docker build 실패 | 이미지 자체가 만들어지지 않음 |
| 이미지 산출물 생성·전달 실패 | 이미지는 빌드됐지만 업로드 작업이 받지 못함 |
| 이미지 load 실패 | 전달된 파일을 로컬 이미지로 복원하지 못함 |
| tag 지정 실패 | Harbor용 최종 이름을 만들지 못함 |
| 인증 실패 | Harbor에 push할 권한을 얻지 못함 |
| push 실패 | 네트워크, 권한, 정책 등의 이유로 Harbor 저장이 완료되지 않음 |

따라서 TeamCity의 이미지 빌드 성공 표시만 보고 Harbor 업로드까지 성공했다고 판단하면 안 된다.

## 6. 반드시 이해해야 할 핵심

1. **Harbor는 컨테이너가 아니라 이미지를 저장한다.** 실행은 나중에 Kubernetes가 담당한다.
2. **Registry, repository, tag는 서로 다른 범위다.** 저장소 서버, 이미지 계보, 특정 버전 이름의 관계다.
3. **Tag는 사람이 읽기 쉬운 이름이지만 기본적으로 변경될 수 있다.** Digest는 이미지 내용에 묶인 식별자다.
4. **리비전 tag는 소스와 이미지와 배포 기록을 연결한다.** `latest`만 사용하는 것보다 추적과 롤백이 쉽다.
5. **리비전 tag도 덮어쓰면 의미가 흔들린다.** 고유 tag와 불변 정책이 함께 필요하다.
6. **Docker build와 Harbor push는 별도 단계다.** 빌드 성공이 저장 성공을 보장하지 않는다.
7. **Harbor 저장과 실제 배포도 별도 단계다.** 배포 설정이 새 tag를 가리켜야 다음 과정이 시작된다.

한 문장으로 압축하면 다음과 같다.

> Harbor는 TeamCity가 만든 런타임 이미지를 repository와 리비전 tag로 보관하고, 이후 배포 시스템과 Kubernetes가 정확한 이미지 버전을 가져갈 수 있게 제공하는 사설 레지스트리다.

- Harbor 설치와 고가용성 구성

## 8. 확인 질문과 답

### 1. 컨테이너 레지스트리란 무엇이며 Harbor에는 무엇이 저장되는가?

컨테이너 레지스트리는 이미지를 저장하고 다른 장비에 배포하는 서버다. Harbor에는 실행 중인 컨테이너가 아니라 이미지 레이어, 이미지 설정, manifest, tag, digest와 관련 메타데이터가 저장된다.

### 2. Registry, Harbor Project 또는 Namespace, Repository, Tag는 어떤 관계인가?

- Registry는 Harbor 서버 전체다.
- Harbor Project 또는 Namespace는 repository와 접근 권한을 묶는 논리 공간이다.
- Repository는 같은 목적의 이미지 버전들이 모이는 이름이다.
- Tag는 repository 안에서 특정 이미지 버전을 가리키는 사람이 읽기 쉬운 이름이다.

큰 범위부터 표현하면 `Registry → Project 또는 Namespace → Repository → Tag` 관계다.

### 3. Tag와 Digest의 차이는 무엇인가?

Tag는 사람이 정한 버전 이름이며 정책에 따라 다른 이미지에 다시 붙일 수 있다. Digest는 이미지 내용으로 계산한 해시이므로 이미지 내용이 달라지면 반드시 함께 달라진다. 읽기와 운영에는 tag가 편하고, 정확히 같은 이미지인지 검증할 때는 digest가 더 강한 근거다.

### 4. 예시 이미지 주소의 구성은 어떻게 나뉘는가?

```text
registry.example.com/game/runtime-dev-x64:rev-12345
```

- Registry: `registry.example.com`
- Harbor Project 또는 Namespace: `game`
- Repository: `runtime-dev-x64`
- Tag: `rev-12345`

### 5. Push와 pull의 방향은 각각 어떻게 되는가?

- Push는 빌드 장비의 로컬 이미지를 Harbor로 올리는 방향이다.
- Pull은 Harbor의 이미지를 Kubernetes 노드나 개발 장비로 내려받는 방향이다.

```text
TeamCity ── push ──▶ Harbor ── pull ──▶ 실행 장비
```

### 6. Docker build가 성공했어도 Harbor에 이미지가 없을 수 있는 이유는 무엇인가?

Docker build는 빌드 장비의 로컬 저장소에 이미지를 만드는 작업이다. Harbor 저장은 별도의 인증, tag 지정, 네트워크 전송과 push 작업이 성공해야 완료된다. 따라서 build가 성공해도 이미지 산출물 전달이나 인증 또는 push가 실패하면 Harbor에는 이미지가 없다.

### 7. `latest`보다 리비전 기반 tag가 추적과 롤백에 유리한 이유는 무엇인가?

`latest`가 가리키는 이미지는 새 push에 따라 계속 달라질 수 있다. `rev-12345` 같은 리비전 tag는 소스 변경 번호, TeamCity 빌드, Harbor 이미지와 배포 설정을 같은 식별자로 연결한다. 어느 소스에서 만든 이미지인지 찾고 이전 리비전으로 돌아가기 쉬워진다.

### 8. 리비전 기반 tag를 사용하면서 같은 tag를 덮어쓰면 어떤 문제가 생기는가?

같은 `rev-12345`가 시간에 따라 서로 다른 이미지 내용을 가리키게 된다. 일부 장비는 이전 이미지를 캐시하고 다른 장비는 새 이미지를 받을 수 있으며, 장애 조사와 롤백 때 실제 실행 내용을 확정하기 어려워진다. 리비전 tag는 재사용하지 않고 필요하면 Harbor의 불변 tag 정책으로 덮어쓰기를 차단해야 한다.

### 9. 이미지 파일 산출물을 build와 push 작업 사이에 전달하는 이유는 무엇인가?

이미지 제작과 레지스트리 업로드를 서로 다른 TeamCity 작업이나 Agent에서 수행할 수 있게 하기 위해서다. 빌드 작업은 이미지를 파일로 저장해 산출물로 넘기고, 업로드 작업은 그 파일을 불러와 Harbor용 이름을 붙인 뒤 push한다. 덕분에 빌드 실패와 업로드 실패를 구분하고 각 단계의 책임을 나눌 수 있다.

### 10. Harbor에 새 이미지가 올라가면 실제 서버도 곧바로 새 버전으로 바뀌는가?

아니다. Harbor는 이미지를 저장할 뿐 실행하지 않는다. 배포 설정이 새 repository와 tag를 가리키도록 변경되고, ArgoCD가 변경을 감지한 뒤 Kubernetes가 새 이미지를 pull하여 컨테이너를 교체해야 실제 서버 버전이 바뀐다.

### 이번 단계 요약 답안

TeamCity가 만든 이미지는 빌드 장비에만 존재하므로 공용 레지스트리인 Harbor에 push해야 한다. Harbor에는 이미지를 구성하는 레이어와 manifest가 repository와 tag별로 저장된다. 리비전 tag는 소스와 이미지를 연결하지만 같은 tag를 덮어쓰면 그 의미가 달라지므로 고유하게 유지해야 한다. Build, 이미지 산출물 전달, Harbor push, 실제 서버 배포는 각각 별도의 성공·실패 상태다.

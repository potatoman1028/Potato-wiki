# 1단계 — 이미지와 컨테이너

상위 문서: [[00_프로젝트_홈|게임 서버 배포 학습]]

## 이번 단계의 목표

이 문서를 읽은 뒤에는 다음 문장을 자신의 말로 설명할 수 있어야 한다.

> 이미지는 서버를 실행하는 데 필요한 내용을 묶은 실행 설계도이고, 컨테이너는 그 설계도로 실제 실행한 프로세스다.

게임 서버 프로젝트의 Linux/Kubernetes 흐름에서는 **코드와 빌드 결과를 동일하게 운반할 수 있는 이미지로 만든 뒤**, 그 이미지를 Kubernetes에서 컨테이너로 실행한다.

다만 이미지는 릴리스 전체와 같은 말이 아니다. 서버 에셋과 DB 스키마처럼 별도 경로로 배포되는 산출물이 있으며, Windows 환경에는 이미지 대신 압축된 서버 패키지와 공유 저장소를 사용하는 실행 경로도 있다. 이번 단계에서는 그중 컨테이너 실행 경로의 출발점만 배운다.

## 1. 이것이 무엇인가

### 컨테이너가 등장한 이유

서버 프로그램만 전달해서 실행하면 대상 장비마다 운영체제, 런타임, 라이브러리, 파일 경로와 설정이 다를 수 있다. 개발 PC에서는 동작했지만 배포 서버에서는 동작하지 않는 문제가 생기는 이유다.

컨테이너 방식은 애플리케이션과 실행에 필요한 파일을 정해진 형태로 묶고, 실행할 때 격리된 공간을 제공한다. 덕분에 개발·테스트·운영 환경에서 **같은 이미지**를 실행 대상으로 삼을 수 있다.

### 이미지와 컨테이너

두 용어는 반드시 분리해서 생각해야 한다.

| 구분 | 이미지(Image) | 컨테이너(Container) |
| --- | --- | --- |
| 비유 | 프로그램 설치 파일 또는 붕어빵 틀 | 설치되어 실행 중인 프로그램 또는 만들어진 붕어빵 |
| 상태 | 실행 전의 읽기 중심 템플릿 | 실제 프로세스가 실행되는 격리 공간 |
| 개수 | 하나를 보관하고 재사용할 수 있음 | 같은 이미지에서 여러 개 만들 수 있음 |
| 포함하는 것 | 애플리케이션, 런타임, 라이브러리, 기본 파일, 기본 실행 명령 | 이미지 내용 + 실행 시 설정 + 쓰기 가능한 계층 + 실행 프로세스 |
| 종료하면 | 이미지에는 영향 없음 | 프로세스가 멈춤. 컨테이너 내부 변경은 삭제 시 함께 사라질 수 있음 |

핵심 관계는 다음과 같다.

```text
이미지 1개
  ├─ ControlServer 컨테이너 1개
  ├─ GameWorker 컨테이너 1개
  ├─ GameWorker 컨테이너 2개
  └─ GatewayServer 컨테이너 1개
```

같은 이미지에서 여러 컨테이너를 만들 수 있으며, 각 컨테이너는 별도의 프로세스와 실행 시 설정을 가질 수 있다.

### 가상머신과 컨테이너

가상머신은 일반적으로 각 가상머신 안에 게스트 운영체제 전체를 둔다. 컨테이너는 호스트의 운영체제 커널을 공유하면서 프로세스와 파일·네트워크 공간을 격리한다.

| 관점 | 가상머신 | 컨테이너 |
| --- | --- | --- |
| 격리 단위 | 운영체제를 포함한 가상 컴퓨터 | 격리된 프로세스 실행 환경 |
| 크기와 시작 | 비교적 크고 시작이 느림 | 비교적 작고 시작이 빠름 |
| 운영체제 | 게스트 OS 포함 | 호스트 커널 공유 |
| 주 용도 | 강한 격리, 서로 다른 OS 실행 | 애플리케이션 배포의 일관성과 빠른 복제 |

컨테이너가 가상머신을 완전히 대체하는 것은 아니다. 실제 Kubernetes 노드 자체는 가상머신일 수 있고, 그 노드 위에서 여러 컨테이너가 실행될 수 있다.

## 2. 왜 필요한가

게임 서버 프로젝트의 Linux/Kubernetes 배포 흐름에서 이미지는 코드와 Kubernetes 사이의 운반 단위다.

```text
소스 코드
  → 빌드하여 서버 실행 파일 생성
  → 실행 파일과 .NET 런타임 등을 이미지로 포장
  → Harbor에 저장
  → Kubernetes 노드가 이미지 다운로드
  → 컨테이너로 실행
```

이 구조가 주는 중요한 효과는 다음과 같다.

- TeamCity가 만든 정확한 결과물을 Harbor에 보관할 수 있다.
- 개발자가 직접 운영 노드에 파일을 복사하지 않아도 된다.
- 여러 노드가 같은 이미지를 받아 동일한 서버 실행 환경을 만들 수 있다.
- 특정 이미지 태그를 다시 지정해 이전 버전으로 돌아갈 수 있다.
- GameWorker가 더 필요하면 같은 이미지에서 실행 인스턴스를 추가할 수 있다.

즉, 이미지는 단순 압축 파일이 아니라 **배포할 서버 버전을 식별하고 반복 실행하기 위한 표준 단위**다.

그러나 이미지가 릴리스의 모든 항목을 담는다고 단정하면 안 된다.

```text
하나의 릴리스
  ├─ 서버 실행 이미지       → Harbor → Kubernetes
  ├─ 환경별 설정            → 배포 설정 저장소 → 컨테이너에 주입
  ├─ 서버·클라이언트 에셋   → 별도 산출물 경로
  └─ DB 스키마·migration    → 별도 DB 배포 경로
```

각 항목의 실제 경로는 뒤에서 배우지만, 서로 호환되는 리비전과 순서로 배포되어야 한다는 점은 지금부터 기억한다.

## 3. 주요 구성 요소

### Dockerfile

Dockerfile은 이미지를 만드는 절차를 적은 파일이다. 보통 다음 내용을 선언한다.

- 어떤 기반 이미지에서 시작할지
- 소스나 빌드 결과를 어디로 복사할지
- 빌드 중 어떤 작업을 수행할지
- 실행에 필요한 환경과 작업 폴더를 어떻게 잡을지
- 컨테이너가 시작될 때 기본으로 어떤 프로세스를 실행할지

Dockerfile 자체가 이미지는 아니다. **Dockerfile을 입력으로 빌드한 결과가 이미지**다.

### 이미지 레이어와 빌드 캐시

이미지는 여러 변경 단계를 겹친 레이어 구조로 만들어진다. 기반 런타임 설치, 애플리케이션 복사 같은 단계가 각각 재사용 가능한 층이 될 수 있다.

앞부분이 변하지 않았다면 Docker는 이전 빌드 결과를 캐시로 재사용할 수 있다. 반대로 앞 단계에서 복사한 파일이 매번 달라지면 그 뒤 단계도 다시 실행될 수 있다. 이 원리는 나중에 실제 프로젝트 Dockerfile의 빌드 속도와 구조를 볼 때 자세히 다룬다.

### 컨테이너 파일 시스템

컨테이너가 시작되면 이미지의 읽기 중심 레이어 위에 해당 컨테이너만의 쓰기 가능한 레이어가 생긴다. 서버가 실행 중 만든 임시 파일은 여기에 기록될 수 있다.

하지만 컨테이너를 삭제하고 새로 만들면 그 쓰기 계층도 사라진다고 생각하는 것이 안전하다. 반드시 남아야 하는 로그나 데이터는 컨테이너 내부에만 두지 않고 Volume 같은 외부 저장 공간에 연결해야 한다. 이 내용은 8단계에서 다룬다.

### 실행 시 주입하는 값

이미지를 바꾸지 않고 컨테이너마다 다르게 줄 수 있는 대표 요소는 다음과 같다.

| 요소 | 역할 | 예시 |
| --- | --- | --- |
| 환경 변수 | 실행 환경에 따라 달라지는 값 전달 | 환경 이름, 기능 스위치 |
| 실행 명령 | 이미지의 기본 명령을 다른 프로세스로 교체 | ControlServer 대신 GameWorker 실행 |
| 포트 연결 | 컨테이너의 네트워크 포트를 외부와 연결 | GatewayServer가 사용하는 포트 노출 |
| 마운트 | 외부 파일이나 저장 공간을 컨테이너 경로에 연결 | 설정 파일, 로그 폴더 |

설정과 민감 정보는 성격이 다르다. 비밀번호나 토큰을 이미지에 넣으면 이미지를 받은 곳마다 정보가 복제되므로, 나중에 ConfigMap과 Secret을 통해 분리하는 이유를 배운다.

### 멀티 스테이지 빌드

서버를 컴파일하려면 SDK와 빌드 도구가 필요하지만, 완성된 서버를 실행할 때는 더 작은 런타임만 있으면 되는 경우가 많다.

멀티 스테이지 빌드는 하나의 Dockerfile 안에서 다음처럼 역할을 나눈다.

```text
빌드 단계: SDK + 소스 코드 → 컴파일된 결과물
실행 단계: 작은 런타임 + 컴파일된 결과물 → 최종 이미지
```

최종 이미지에 빌드 도구와 전체 소스를 넣지 않아도 되므로 이미지 크기와 불필요한 구성 요소를 줄일 수 있다.

## 4. 다른 기술과 어떤 관계인가

이 단계에서 각 기술의 역할 경계를 잡아 두면 뒤가 쉬워진다.

| 기술 | 이미지·컨테이너와의 관계 |
| --- | --- |
| TeamCity | 소스를 빌드하고 Docker 이미지 생성을 자동화하는 CI 도구 |
| Harbor | 완성된 이미지를 태그와 함께 보관하는 레지스트리 |
| Kubernetes | 원하는 이미지를 지정된 수의 컨테이너로 실행하고 유지하는 시스템 |
| Helm | 어떤 이미지와 설정으로 Kubernetes 리소스를 만들지 템플릿화하는 도구 |
| ArgoCD | Git에 기록된 Helm·Kubernetes 설정을 실제 클러스터 상태와 맞추는 도구 |

Docker가 컨테이너 하나를 실행하는 방법을 제공한다면, Kubernetes는 여러 노드에서 많은 컨테이너의 배치·교체·복구를 지속적으로 관리한다.

## 5. 실제 프로젝트에서는 어디에 사용되는가

2026-08-20 로컬 소스의 서버 런타임 Dockerfile을 기준으로 확인한 구조다. 공개 문서에서는 실제 프로젝트명, 파일명, 실행 파일명을 역할명으로 치환한다.

1. .NET SDK 기반 `build` 단계에서 ControlServer, GameWorker, GatewayServer 역할의 프로젝트 패키지를 복원한다.
2. `publish` 단계에서 세 서버를 같은 출력 경로에 게시한다.
3. .NET Runtime 기반 `base` 단계에 실행에 필요한 라이브러리와 로그 경로를 준비한다.
4. `final` 단계에 게시 결과, 서버 에셋, 기본 설정 파일을 복사한다.
5. 기본 명령은 ControlServer 역할의 실행 파일을 시작한다.

따라서 최종 런타임 이미지 안에는 세 서버의 실행 결과가 함께 들어간다. 그러나 **이미지 하나가 세 서버를 동시에 실행한다는 뜻은 아니다.** 컨테이너를 만들 때 실행 명령을 선택한다.

```text
동일한 게임 서버 runtime 이미지
  ├─ 기본 명령 사용               → ControlServer 프로세스
  ├─ 실행 명령을 GameWorker로 변경  → GameWorker 프로세스
  └─ 실행 명령을 GatewayServer로 변경 → GatewayServer 프로세스
```

로컬 Docker Compose 구성에서도 세 서비스가 같은 이미지와 같은 이미지 태그를 사용하고, 각 서비스의 실행 명령만 해당 역할의 실행 파일로 바꾸는 것을 확인할 수 있다. GatewayServer에는 별도의 포트 연결도 지정되어 있다.

나중에 Kubernetes를 배울 때 이 구조는 다음 질문으로 이어진다.

- 세 서버 실행 인스턴스를 Kubernetes가 각각 어떤 단위로 만들고 관리하는가?
- GameWorker를 여러 개 만들면 실행 인스턴스별 설정과 네트워크는 어떻게 달라지는가?
- 같은 이미지에 들어 있는 기본 설정을 환경별 설정이 어떻게 덮어쓰는가?

이 질문에 쓰이는 `Pod`, `Deployment`, `Rollout`은 지금 이해하지 않아도 된다. Pod와 Deployment는 5단계에서, Rollout은 11단계에서 처음부터 설명한다. 바로 다음 2단계에서는 계속 Dockerfile과 이미지 빌드만 다룬다.

실제 배포 설정 저장소의 Helm 설정과 리소스별 실행 명령은 해당 단계에서 확인이 필요하다.

## 6. 반드시 이해해야 할 핵심

1. **이미지와 컨테이너는 다르다.** 이미지는 저장하고 전달하는 템플릿이며, 컨테이너는 그 이미지로 만든 실행 인스턴스다.
2. **한 이미지에서 여러 컨테이너를 만들 수 있다.** GameWorker를 여러 개 실행한다고 이미지를 여러 번 빌드할 필요는 없다.
3. **이미지가 같아도 실행 명령과 설정은 다를 수 있다.** 게임 서버 프로젝트는 같은 런타임 이미지로 서로 다른 서버 프로세스를 실행한다.
4. **컨테이너 내부 파일은 영구 저장소가 아니다.** 사라지면 안 되는 값은 외부 설정과 볼륨으로 분리한다.
5. **이미지는 배포 흐름의 계약이다.** TeamCity가 만들고 Harbor가 보관하며 Kubernetes가 받아 실행한다.
6. **이미지는 릴리스 전체가 아니라 핵심 산출물 중 하나다.** 설정, 에셋, DB 스키마는 다른 경로로 전달될 수 있다.

한 문장으로 압축하면 다음과 같다.

> 게임 서버 런타임 이미지는 세 서버를 실행할 재료를 담은 불변에 가까운 패키지이고, ControlServer·GameWorker·GatewayServer 컨테이너는 그 패키지에서 선택한 서버 프로세스를 실제로 실행한 인스턴스다.

- Linux namespace와 cgroup의 구현 원리
- 이미지 manifest와 OCI 규격의 세부 구조
- Kubernetes가 Docker 대신 containerd 같은 런타임을 사용하는 내부 과정
- Pod, Deployment, ReplicaSet의 구체적인 관계 — 5단계에서 학습
- Rollout과 고급 배포 전략 — 11단계에서 학습
- Harbor의 권한, 복제, 취약점 검사 설정
- 멀티 아키텍처 이미지 빌드

지금은 `코드 → 이미지 → 컨테이너 프로세스` 관계만 단단히 잡으면 된다.

## 8. 스스로 확인할 질문

아래 질문에 문서를 보지 않고 자신의 말로 답해 본다.

1. Docker 이미지와 컨테이너의 차이는 무엇인가?
2. 같은 이미지에서 GameWorker 컨테이너 두 개를 만들 수 있는 이유는 무엇인가?
3. 런타임 이미지 하나로 서로 다른 세 서버를 실행할 수 있는 방법은 무엇인가?
4. Dockerfile과 Docker 이미지의 관계는 무엇인가?
5. 서버가 컨테이너 내부에 남긴 로그를 컨테이너 삭제 후에도 보존하려면 왜 별도 저장 공간이 필요한가?
6. TeamCity, Harbor, Kubernetes는 이미지에 대해 각각 어떤 역할을 맡는가?
7. Docker 이미지에 서버 실행 파일이 들어 있다고 해서 그 이미지 하나만으로 전체 릴리스가 완성됐다고 말할 수 없는 이유는 무엇인가?

### 통과 기준

다음 상황을 막힘없이 설명할 수 있으면 1단계를 이해한 것이다.

> “Harbor에 게임 서버 이미지가 하나 있는데, Kubernetes에서는 ControlServer 1개, GameWorker 3개, GatewayServer 1개가 실행 중이다. 이미지가 하나인데 어떻게 서버가 다섯 개일 수 있는가?”
